用过廉价海外 VPS（RackNerd、CloudCone、AWS Lightsail 之类）的人大概都遇到过这种落差：

```text
白天 14:00 → YouTube 4K 秒开，Speedtest 跑满 100Mbps
晚上 21:00 → 720p 缓冲半天，Speedtest 不到 5Mbps
```

常见的第一反应是「晚高峰带宽不够」。但实际原因不是带宽，是丢包，而 TCP 恰好最怕丢包。

## 一、TCP 在丢包下会崩

### 吞吐量和丢包率的关系

TCP 的吞吐量有一个经典的理论上限：

```text
Throughput ≤ MSS / (RTT × √p)
```

- MSS 是最大报文段长度，通常 1460 字节
- RTT 是往返时延，中美之间大约 150ms
- p 是丢包率

代入实际数字：

| 丢包率 p | TCP 理论最大吞吐量 |
|----------|-------------------|
| 0.1% | 约 150 Mbps |
| 1% | 约 50 Mbps |
| 5% | 约 22 Mbps |
| 10% | 约 16 Mbps |

注意这是理论最大值。实际中拥塞控制算法（Cubic / BBR）遇到丢包还会主动降窗，真实吞吐往往只有理论值的一半。

### 晚高峰的丢包发生在哪一跳

拿一台 RackNerd 洛杉矶的 VPS，在 21:00 执行：

```bash
mtr -r -c 100 你的VPS_IP
```

### TCP 为什么扛不住

TCP 的基本假设是：丢包意味着拥塞。所以一旦丢包，它会做三件事：

1. 减小拥塞窗口，发送速率砍半甚至降到 1 MSS
2. 等待 RTO（重传超时，通常不低于 200ms）再重发丢失的包
3. 从很小的窗口重新慢启动爬升

丢包率到 10% 到 20% 时，这套机制会陷入一个自我强化的循环：丢包导致降速，降速伴随重传，重传让更多包排队，排队推高延迟，延迟触发超时重传，然后进一步降速。

用 Wireshark 抓一下能看到满屏的 `TCP Retransmission` 和 `TCP Dup ACK`，有效吞吐不到链路能力的一成。

## 二、换掉 TCP

既然问题出在 TCP 的拥塞控制上，思路就是不用它。

### UDP 为什么不怕丢包

UDP 是无连接的，没有拥塞窗口、没有重传、没有慢启动。你发多少它就送多少，路上丢了多少它不管。

但纯 UDP 不可靠，丢了就是丢了。所以需要的是在 UDP 之上重新实现可靠传输的协议，也就是 QUIC。

### QUIC 与 Hysteria 2

QUIC 是 Google 设计的协议，HTTP/3 就跑在它上面。它在 UDP 之上提供了：

- 前向纠错（FEC）：发数据时附带冗余信息，少量丢包能就地恢复，不用重传
- 连接迁移：从 WiFi 切到 4G 不断连
- 0-RTT 握手：重连时省掉握手延迟
- 多路复用：一个连接跑多个流，避免队头阻塞

Hysteria 2 是基于 QUIC 改的，针对高丢包链路做了调整：

| 特性 | 传统 TCP（SS / VMess） | Hysteria 2（QUIC） |
|------|----------------------|-------------------|
| 传输层 | TCP | UDP |
| 丢包处理 | 降速加重传 | FEC 加激进重传 |
| 握手 | TCP 三次 + TLS | QUIC 0-RTT |
| 队头阻塞 | 有 | 无 |
| 拥塞控制 | Cubic / BBR | 自定义的 Brutal |
| 伪装 | TLS | QUIC，天然像 HTTP/3 |

### Brutal 算法

Hysteria 2 最核心的改动是 Brutal 拥塞控制，行为和名字一致。

传统 TCP 的逻辑是「堵车了就慢点开」；Brutal 的逻辑是不看路况，按你设定的目标带宽恒速发送。你给它 50Mbps，它就一直按 50Mbps 发，丢多少包都不降速，丢掉的部分靠 FEC 和激进重试补回来。

这个做法确实粗暴。如果运营商有深度包检测，大量异常 UDP 流量可能触发 QoS 限速甚至临时阻断——这是它的代价，后面第四节会讲怎么处理。

## 三、实测对比

同一台 RackNerd 洛杉矶 VPS，白天和晚高峰各测一次。

白天 14:00：

| 协议 | 下载速度 | YouTube 画质 | 延迟 |
|------|---------|-------------|------|
| Shadowsocks（TCP） | 85 Mbps | 4K 秒开 | 160ms |
| Hysteria 2（UDP） | 90 Mbps | 4K 秒开 | 158ms |

链路好的时候两者差不多，TCP 并不吃亏。

晚高峰 21:30：

| 协议 | 下载速度 | YouTube 画质 | 延迟 |
|------|---------|-------------|------|
| Shadowsocks（TCP） | 2.3 Mbps | 720p 缓冲 | 360ms |
| Hysteria 2（UDP） | 52 Mbps | 4K 秒开 | 175ms |

差了二十多倍。原因前面已经讲清楚了：12% 的丢包率下 TCP 的拥塞控制已经失效，而 QUIC 基本不受影响。

## 四、部署

### 服务端

```bash
bash <(curl -fsSL https://raw.githubusercontent.com/Misaka-blog/hysteria-install/main/hy2/hysteria.sh)
```

选「安装 Hysteria 2」，用自签证书，设置端口（比如 54321），记下输出的 `hysteria2://` 链接。

### 客户端

- **Windows**：v2rayN 6.0 以上，直接 `Ctrl+V` 粘贴 `hysteria2://` 链接
- **Android**：NekoBox，粘贴后自动识别
- **iOS**：Shadowrocket，类型选 Hysteria2，打开「允许不安全连接」
- **macOS / Linux**：用 `sing-box` 或 `hysteria` 命令行

## 五、建议两个协议一起用

我不建议只留 Hysteria 2，有三个现实问题：

1. **UDP QoS**：部分运营商和校园网对 UDP 限制很严，Hy2 可能被限到 1Mbps
2. **断流**：异常 UDP 流量可能被 DPI 临时阻断五到十分钟
3. **耗电**：手机上 UDP 持续传输比 TCP 费电

所以合理的分工是：白天或者需要省电时用 Shadowsocks；晚高峰或者需要速度时切 Hysteria 2；万一 Hy2 被 QoS 限住，还有 Shadowsocks 保底。

在 v2rayN 里把两个节点都加进去，设置自动切换或者手动切都行。

## 小结

这篇真正想说的其实只有一句：不是 VPS 不够快，是 TCP 在丢包场景下不适合这条链路。

想明白这一点，就能理解 Hysteria 2 为什么能救回一条烂线路，也能理解它为什么会被运营商盯上。协议没有优劣，只有适不适合当前的链路状况。
