> **TL;DR**：这篇的上一版描述的工作流已经不存在了——它跟着旧站一起下线了。新版更短：写完跑一个脚本，20 秒后文章在线上，全程不重新部署。因为文章正文根本不在镜像里。

这篇文章有过一个版本，讲的是 Obsidian + Templater 生成 frontmatter、Node 脚本扫描目录生成 `posts.json`、再用 PowerShell 一键发布。

那套东西现在**一个都不剩了**。旧站下线时，`standardize_posts.js`、`publish.ps1`、连同 `posts.json` 本身，一起被删掉了。留着一篇介绍不存在的东西的文章，比没有文章更糟。

所以重写一遍。顺便说，新的这套比旧的**短得多**——不是因为我更能写脚本了，而是因为架构变了，很多步骤根本没有存在的必要。

## 先看结论

现在发一篇文章是这样：

```bash
cd web
node scripts/new-post.mjs "文章标题" --slug my-post --category 教程 --tags Docker,教程
# → content/drafts/2026-08-02-my-post.md，用什么编辑器都行

# 写完
node scripts/publish-post.mjs 2026-08-02-my-post.md --dry-run   # 先看它打算干什么
node scripts/publish-post.mjs 2026-08-02-my-post.md             # 真发
```

第二条命令跑完大约 20 秒，文章就在线上了。**没有构建，没有部署，没有重启容器。**

## 为什么不再需要 posts.json

旧版流程里最烦的一步是「更新索引」：写完文章要跑脚本扫描整个目录、生成一个 `posts.json`，前端再去读它。忘了跑，文章就不出现。

新站直接把这一步删了。文章索引是**请求时实时算的**：

```javascript
// lib/posts.js
export function getPostsIndex() {
    if (cache && Date.now() - cacheTime < 30_000) return cache;
    const files = fs.readdirSync(postsDir()).filter((f) => f.endsWith('.md'));
    const posts = files.map((file) => {
        const fm = parseFrontMatter(fs.readFileSync(path.join(dir, file), 'utf8'));
        return { title: fm.title, date: fm.date, /* … */ file };
    });
    posts.sort((a, b) => (b.date || '').localeCompare(a.date || ''));
    // …缓存 30 秒
}
```

读目录 + 解析 frontmatter，缓存 30 秒。十九篇文章的站点，这点开销可以忽略，换来的是**「发文 = 丢一个 .md 文件」**这条不变量。没有中间产物，也就没有中间产物过期的问题。

## 为什么发文章不需要部署

这是整套流程里最反直觉、也最省时间的一点。

站点跑在 Docker 容器里，改代码要重新构建镜像、换容器，一次三到五分钟。但**文章正文不在镜像里**——它在一个挂载卷上：

```
宿主 /www/wwwroot/shadowquake-v2/content/posts  →  容器 /app/content/posts
```

容器读的是宿主的目录。往那个目录里 `scp` 一个 `.md`，容器**当场**就能读到。加上索引只缓存 30 秒、正文渲染结果按文件 mtime 失效，于是：

| 改什么 | 要不要部署 |
|---|---|
| 文章正文 | 不要 |
| 封面图（放挂载卷里的话） | 不要 |
| 页面代码、样式、组件 | 要 |

发布脚本因此只做三件事：把文件传上去、清掉 CDN 边缘缓存、验证线上真的 200。

## 脚本替我做的三件事

### 1. 只让我写「只有我知道」的字段

frontmatter 有九个字段，但其中三个是纯机械的：摘要、阅读时长、最后修改时间。以前它们是手写的，于是——

我这十九篇文章的 `excerpt`，**几乎每一条都是把标题又抄了一遍**。因为写的时候懒，直接复制标题粘上去。结果文章卡片上只有两行摘要，第一行永远在重复右边已经写着的标题，等于白丢一行。前端甚至为此打了个补丁，展示时把重复的标题前缀剥掉。

现在这三个字段一律由脚本算。摘要优先取开头的 TL;DR 引用块——那本来就是我自己写的一句话总结，比任何自动截取都准：

```javascript
// 跳过与标题重复的 H1，跳过表格和分隔线，取第一个像样的段落
const titleNorm = norm(title || '');
for (const raw of blocks) {
    const s = demote(raw);
    if (titleNorm && norm(s) === titleNorm) continue;   // 与标题重复
    if (s.length < 12) continue;                        // 太短的过渡句
    return s.replace(/^TL;?DR[:：]?\s*/i, '');
}
```

新建文章的模板里，只留了标题、日期、分类、标签四个要填的——封面都可以空着，空的话会自动落到分类默认图。

### 2. 阅读时长：拿自己的旧数据拟合

「X 分钟阅读」这种数字，随便写个公式都不算错，但我想让它至少和我自己的手感一致。

于是拿现有十九篇手写的 `readTime` 反过来拟合系数。结果是 `中文字数 / 250 + 代码行数 / 15 + 英文词数 / 200`。

代码必须单独算：有一篇只有 777 个中文字，却有 94 行代码，把代码丢掉会算成 3 分钟，我当初手写的是 8 分钟。

但代码也不能直接线性加——另一篇嵌了 159 行 HTML 片段，线性算下来 20 分钟，我手写的是 14。所以加了一条上限：

```javascript
const prose = cjk / 250 + words / 200;
// 扫代码的时间不超过读正文的时间：代码块越长越是复制粘贴，不是逐行读
const code = Math.min(codeLines / 15, prose);
return Math.max(1, Math.round(prose + code));
```

加上这条上限后，十九篇里有十五篇落在我手写值的 ±1 分钟内。顺带一提，那些手写值**自己就不自洽**——同样 800 字左右的两篇，一篇我写 3 分钟，另一篇写 4 分钟。

### 3. 图片：让我继续用 PicList，但线上不留外链

我习惯用 PicList 传图，随手复制一个地址粘进文章。问题是那些地址多半在境外。

这个站有一条硬规矩：**前端不允许有跨境依赖**。大陆实测，字体 CDN 首字节 4.89 秒，cdnjs 3.66 秒，图床整图下载能抖到 15 秒——而文章封面基本就是页面的最大内容元素，它慢，整页就慢。

但我不想为此改掉自己的上传习惯。所以把这件事推给发布脚本：它扫描正文和封面里所有绝对地址，凡是不在自己域名下的，就抓下来、转成 webp、传到服务器的图片目录，再把文章里的地址改写掉。

```javascript
// 文件名取源地址的 sha1 前 8 位：
// 同一张图重复发不会重复占空间，换了图就是新文件名，也就不用为图片清缓存
const hash = crypto.createHash('sha1').update(url).digest('hex').slice(0, 8);
await sharp(src).resize({ width: 1600, withoutEnlargement: true })
                .webp({ quality: 82 }).toFile(out);
```

对我来说，写作时的动作一点没变；对读者来说，页面上一个跨境请求都没有。

顺便：下载这些图本身多半要过代理，脚本用 `curl` 而不是 `fetch` 就是为了让它读 `HTTPS_PROXY`。

## 防呆比功能重要

写脚本的时候，我花在「防止自己犯错」上的代码，比花在功能上的多。

**frontmatter 的解析器很脆。** 它是手写的，按第一个冒号切、逐行处理。这意味着任何一个字段值里出现换行，后面所有字段都会被冲掉。所以序列化的时候强制压平：

```javascript
const clean = (s) => String(s).replace(/[\r\n]+/g, ' ').replace(/-{3,}/g, '—').trim();
```

**先看再发。** `--dry-run` 把所有要写入的字段、要镜像的图片、最终地址全打印出来，一个字节都不碰服务器。`--preview` 更进一步，把成品放进本地目录，用真实的文章列表、上下篇、相关推荐看排版。

**发布后自己验证。** 不是发完就说「完成」，而是真的去请求一次线上地址，检查状态码、检查标题在不在页面里、检查文章有没有进索引。

**提醒我没做完的事。** `--preview` 会在本地留下一个服务器上没有的文件，看着跟已上线的文章一模一样。所以同步脚本会把这类文件单独列出来，告诉我要么发布、要么删掉。

## 它做不到什么

诚实一点，这套流程有明确的边界：

- **没有草稿态**。文章要么在本地、要么就是公开的，没有「传上去但只有我能看」这个中间状态。要做得改应用代码，暂时不值当。
- **slug 发布后不能改**。文件名就是网址，改了等于换地址、丢掉所有外链。所以新建时脚本会拦住中文 slug——中文网址会变成一长串百分号编码。
- **不管拼写和病句**。它只保证格式正确、链路通畅，写得好不好还是我自己的事。

## 和上一版比

| | 上一版 | 现在 |
|---|---|---|
| 索引 | 手动跑脚本生成 `posts.json` | 请求时实时算，缓存 30 秒 |
| 发布 | 更新索引 → 提交 → 部署 | 传文件 → 清缓存 → 验证 |
| 耗时 | 分钟级 | 20 秒左右 |
| 封面 | 随机分配一张外链图 | 抓下来转 webp，落到自己服务器 |
| 摘要/时长 | 手写，经常写错 | 算出来 |

真正让流程变短的不是脚本写得更好，而是**把「必须部署」这个前提去掉了**。这也是我这次最想记下来的一点：优化一条流程之前，先确认里面每一步是不是真的必要。很多时候最快的做法不是把某一步做快，而是发现它压根不用做。

Happy Writing！
